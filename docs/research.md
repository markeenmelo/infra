## Module architecture

- [Dendritic upstream definition](https://github.com/mightyiam/dendritic/blob/6c76240658cf1c840faad557c0e0726064170a65/README.md): every non-entry-point Nix file is a top-level module; features can span configuration classes; lower configurations are module-system values. Flake-parts is common, **not mandatory**; direct `lib.evalModules` is valid. The pattern allows a trivial discovery expression. Avoid proliferating named lower modules or forwarding `specialArgs`; use custom options where the domain needs them. Host identity is an explicit domain submodule here.
- [Nixpkgs module-system manual](https://nixos.org/manual/nixpkgs/stable/#module-system), [deferredModule implementation](https://github.com/NixOS/nixpkgs/blob/93108a538f079596c9a16c72cf03e9322782b6dd/lib/types.nix): deferred values merge by composing imports, and evaluate later with the lower configuration's module arguments. No shared NixOS `pkgs` is required by dendritic composition.
- [flake-parts modules](https://flake.parts/options/flake-parts-modules.html), [system guide](https://flake.parts/system), [source](https://github.com/hercules-ci/flake-parts/tree/31729ca8cbdb4fa927b34e5f4353e6a83f39e993): `flakeModules.modules` provides class-checked deferred module values; `nixosConfigurations` belongs outside `perSystem`. The guide's isolated-NixOS approach fits multiple Nixpkgs inputs. Use one selected input's `nixosSystem` per host; stable top-level lib and developer pkgs do not determine a host's pkgs. [Issue #339](https://github.com/hercules-ci/flake-parts/issues/339) illustrates recursion risks when injecting perSystem packages via host configuration: avoid that route here.
- Chosen flake-parts over raw `evalModules` because it supplies standard flake output plumbing and module classes without an internal framework. `nixpkgs-lib.follows = "nixpkgs-stable"` affects only the top-level evaluator. No import-tree, flake-file or aspect framework is needed. The class wrapper does not assign a module key; the multiply imported SSH value has an explicit key to avoid duplicate persistence entries.

## Storage / impermanence

- **2026-09-09, PR #1 ESP-size review:** the [installation chapter at stable `93108a5`](https://github.com/NixOS/nixpkgs/blob/93108a538f079596c9a16c72cf03e9322782b6dd/nixos/doc/manual/installation/installing.chapter.md) describes reserving 512 MiB for the ESP (its example commands use MB, so they are not a precise binary-size policy). [Locked disko GPT sizing](https://github.com/nix-community/disko/blob/ff8702b4de27f72b4c78573dfb89ec74e36abdf1/lib/types/gpt.nix) passes sizes to [sgdisk](https://www.rodsbooks.com/gdisk/sgdisk.html), whose `M`/`G` units are MiB/GiB. Both pinned boot builders ([stable](https://github.com/NixOS/nixpkgs/blob/93108a538f079596c9a16c72cf03e9322782b6dd/nixos/modules/system/boot/loader/systemd-boot/systemd-boot-builder.py), [unstable `422d1ae`](https://github.com/NixOS/nixpkgs/blob/422d1ae605d7fcd9896412b37dc065c456c0eefb/nixos/modules/system/boot/loader/systemd-boot/systemd-boot-builder.py)) install kernel/initrd files on the boot filesystem, which is the ESP in this baseline (no XBOOTLDR). Before the fix, a synthetic `1M` ESP passed both tracks' assertions and disko-script derivation evaluation. Adopt **512 MiB as a repository safety floor**, not a universally sufficient capacity; actual boot files, retained generations and headroom still need review.
- The ESP guard uses the option's `apply` to validate the merged, syntax-checked value ([pinned module evaluator](https://github.com/NixOS/nixpkgs/blob/93108a538f079596c9a16c72cf03e9322782b6dd/lib/modules.nix)), retaining null and rejecting undersized values even during direct disko evaluation. It does not rely on NixOS toplevel assertions or `types.addCheck`; the latter has an [open type-merging caveat #396021](https://github.com/NixOS/nixpkgs/issues/396021). Both-track regression fixtures force script derivations for accepted/rejected sizes and check missing-size and BIOS behavior. No installation or disk operation is used to test this policy.
- [Disko README](https://github.com/nix-community/disko), [HowTo](https://github.com/nix-community/disko/blob/master/docs/HowTo.md), [quickstart](https://github.com/nix-community/disko/blob/master/docs/quickstart.md), [module source](https://github.com/nix-community/disko/blob/ff8702b4de27f72b4c78573dfb89ec74e36abdf1/module.nix), [examples](https://github.com/nix-community/disko/tree/master/example): `nixosModules.disko` derives filesystems and provisioning scripts; the current output is `system.build.diskoScript`, not deprecated `.disko`. CLI `--mode destroy,format,mount` is destructive. `nixos-generate-config --no-filesystems` avoids duplicate filesystem definitions. EF02 partitions derive GRUB devices automatically; adding the disk again fails the duplicate-device assertion. The [pinned systemd-boot builder](https://github.com/NixOS/nixpkgs/blob/93108a538f079596c9a16c72cf03e9322782b6dd/nixos/modules/system/boot/loader/systemd-boot/systemd-boot-builder.py) maps `canTouchEfiVariables = false` to `bootctl --no-variables`; this repository requires an explicit UEFI NVRAM/fallback choice rather than assuming firmware behavior.
- Disko's latest published release is [v1.13.0](https://github.com/nix-community/disko/releases/tag/v1.13.0), January 2026; this repository locks current master **`ff8702b4de27f72b4c78573dfb89ec74e36abdf1`** for post-release fixes and validates that exact module on both tracks. Its own `nixpkgs` follows stable for upstream tool outputs; the NixOS module obtains **target** `pkgs`, `lib`, and `modulesPath`. This follows upstream's flake integration pattern without collapsing host inputs. [Open partition-UUID behavior work #1294](https://github.com/nix-community/disko/pull/1294) reinforces not treating a provisioning run as a harmless rebuild. Re-evaluate scripts on every disko update; no guarantee of destructive idempotence is assumed.
- [Impermanence README](https://github.com/nix-community/impermanence/blob/7b1d382faf603b6d264f58627330f9faa5cba149/README.org), [module](https://github.com/nix-community/impermanence/blob/7b1d382faf603b6d264f58627330f9faa5cba149/nixos.nix): use `nixosModules.impermanence`; wiping root and durable storage are separate prerequisites. Persistent **and ephemeral** volumes must be `neededForBoot`. Upstream explicitly permits empty follows for its development-only nixpkgs/Home Manager inputs; those remain disabled independently of the fleet's later desktop Home Manager integration. Commit **`7b1d382faf603b6d264f58627330f9faa5cba149`** adds early-mount assertions and includes a machine-id/systemd workaround.
- [Open issue #320](https://github.com/nix-community/impermanence/issues/320) documents stale scripted-initrd Btrfs examples; [#332](https://github.com/nix-community/impermanence/issues/332) documents first-install `/nix`/state migration pitfalls. Choose tmpfs root (also a disko nodev mount) and real Btrfs `/nix` + `/persist` subvolumes; no root-reset script. Preseed/migrate identity and user/service data before reboot. Evaluation compatibility is verified, actual machine boot behavior is not yet tested.

## Kernel 7.x evaluation — 2026-09-09 (historical recommendation)

**Historical comparison:** the subsequently requested implementation is recorded under [native desktop/apps/authentication/Wi-Fi/kernels](#native-desktop-apps-authentication-wi-fi-and-kernels--2026-09-09); it supersedes the earlier explicit-minor recommendation.

The user prefers 7.x. The committed baseline still selects the default **6.18 LTS**: `6.18.49` on stable and `6.18.50` on unstable. The following is source/derivation evaluation, **not benchmarks, builds, boot tests or a kernel change**. No host or lock was changed for this comparison.

- [kernel.org](https://www.kernel.org/) lists **7.2.4** as stable, **7.1.13 as EOL**, and 7.3-rc2 as a prerelease. The [release-policy/LTS table](https://www.kernel.org/category/releases.html) has no 7.x longterm branch; 6.18 is maintained through projected December 2028. Do not call a stable-channel package an LTS kernel, select an EOL 7.0/7.1 just for its major number, or assume 7.x is intrinsically faster/more secure.
- At the existing pins, [stable kernel aliases](https://github.com/NixOS/nixpkgs/blob/93108a538f079596c9a16c72cf03e9322782b6dd/pkgs/top-level/linux-kernels.nix) provide stock **7.2.3**, while [unstable](https://github.com/NixOS/nixpkgs/blob/422d1ae605d7fcd9896412b37dc065c456c0eefb/pkgs/top-level/linux-kernels.nix) provides stock **7.2.4**. Both offer Zen **7.2.3**. XanMod's plain/default alias is **6.18**, not 7.x; its main/latest variant is 7.1.13 on this stable pin (already EOL) and 7.2.4 on unstable. `linux_hardened` is removed for lack of maintenance at both pins. Keep packages within the host's track; a routine researched stable update can refresh its patch level before eventual commissioning.
- The [pinned Zen configuration](https://github.com/NixOS/nixpkgs/blob/422d1ae605d7fcd9896412b37dc065c456c0eefb/pkgs/os-specific/linux/kernel/zen-kernels.nix) enables interactive tuning, full preemption, 1000 Hz and BFQ. These target responsiveness, not guaranteed FPS, throughput or battery improvements; the package also warns it does not exactly reproduce the upstream configuration. Zen is not an AMD-specific kernel. [XanMod's package](https://github.com/NixOS/nixpkgs/blob/422d1ae605d7fcd9896412b37dc065c456c0eefb/pkgs/os-specific/linux/kernel/xanmod-kernels.nix) selects performance-oriented governor/network settings, making it a poor unmeasured default for ThinkPad mobility. Stock already includes modern preemption and CPU power-management support.
