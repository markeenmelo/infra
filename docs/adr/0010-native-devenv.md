# ADR 0010 — Native devenv for local development

- Status: accepted; native CLI selected by the operator (gate-layering/treefmt and explicit single-host live-task amendments folded in)
- Date: 2026-09-12

## Decision

- Root `devenv.nix`/`devenv.yaml`/`devenv.lock` provide the **native** development CLI, replacing `mkShellNoCC`, `perSystem.devPackages` and the justfile. This is the deliberate development-only exception: `flake.nix` remains the production entry point, all `modules/` files remain top-level flake-parts modules, and no host imports devenv. No third package track, parallel devShell or local-flake/self-lock bridge.
- Native devenv assembles the toolbox and task graph; feature-owned scripts, packages and flake checks stay beside their owners. `nix run --no-update-lock-file .#devenv -- shell` bootstraps the CLI without installation. The operator selected unstable developer tools and unversioned `github:cachix/devenv`; exact source revisions live in locks. The production unstable input is named `nixpkgs` (flake-parts, Home Manager and Zen follow it); `nixpkgs-stable` stays explicit. Native Nixpkgs stays locked to the same source as the flake's unstable tools. A repository assertion selects the locked CLI; native checks establish module/task compatibility and exact OpenTofu/provider wrapper parity. `deploy-rs` and `sops-nix` stay production inputs because the fleet consumes their activation helpers and NixOS modules; devenv only exposes their command-line tools.
- **Gate layering:** `repo:check` is the fast inner gate — the native task/lock/tooling contract, one treefmt format check, report-only statix, the ciphertext guard and the whole-fleet inventory, in seconds. `repo:check-full` is the canonical gate for final candidates, deployment preflight and `devenv test`: everything above plus the evaluation oracle, the ciphertext regression suite and `nix flake check -L`. Ciphertext-before-evaluation ordering, uncached safety gates and the no-deployment task boundary remain contract-pinned.
- Argument-taking and credential-bearing operations remain scripts by default. The operator explicitly selected one exception on 2026-09-13: disconnected uncached `deploy:host`, invoked with task inputs `host`, `mode` and an exact public confirmation string. It has no DAG edges, so `repo:*`, shell/test entry and dependency expansion cannot select it. The task requires a private foreground terminal, signed transport, a readable `LOCAL_KEY` whose derived public key matches the selected target, full canonical validation, deployment readiness, strict SSH options, signature checking, interactive sudo and retained automatic/magic rollback before one named deployment. Signer paths/passwords are never task inputs. Readiness refusal, existing-installation disk-plan refusal, tailnet binding, provider isolation, encryption and exact apply confirmation remain preserved.
- One native treefmt declaration (via `devenv.yaml`'s `treefmt-nix` following `nixpkgs`) formats Nix (nixfmt), removes dead bindings (deadnix), applies ShellCheck to all Bash sources including `.envrc`, and runs OpenTofu fmt. Report-only statix stays a separate `repo:lint` because treefmt can only run statix's fixing mode. devenv's own treefmt task is detached from shell entry; the task contract guards that detachment. Formatting is an explicitly invoked operation.
- Operator credentials use existing SOPS plus a small runtime-only JSON allowlist adapter: `tailnet-sops ENCRYPTED.yaml OPERATION` loads exactly the OAuth ID, OAuth secret and existing state passphrase into the guarded OpenTofu process. Never evaluate decrypted values, export them into the shell, source decrypted shell text or write them to task output/cache files. No OpenTofu SOPS data source or SecretSpec evaluation-time loading; host SOPS delivery is unchanged.
- Other integrations: the native OpenTofu language module with the locked provider wrapper and `tofu-ls`; Nix/Bash language servers plus the existing Python checks, formatter and linters; an opt-in `hooks` profile (ordinary shell entry installs no hooks); `.envrc` uses the installed CLI's native direnv integration without downloading shell code. No application services, databases, containers or automatic npm installation.

## Consequences

- Two lock files exist intentionally: unstable updates must synchronize the Nixpkgs node ([procedure](../development.md#locks-and-architecture)); native module/hook updates stay separate from production input updates. Unstable tooling advances OpenTofu/provider versions and the offline artifact checksum, so existing live state is not opened/migrated and old saved plans require separate review.
- Adding a live task increases operator responsibility: an exact `devenv tasks run deploy:host --input ...` command is authorization-sensitive and contacts one target after local gates. Its required null defaults make accidental/no-input task selection fail before evaluation or network access. No real readiness, hardware, storage, credential or deployment fact changes. Native shell/task execution and canonical flake checks are required; evaluation-only or mocked secret tests establish neither real decryption, installation nor deployment.
